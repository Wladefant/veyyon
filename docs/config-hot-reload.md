# Reloading profile routing defaults

After editing the active profile's `config.yml`, send `/reload-config` in the running session (TUI, RPC, or ACP text command). Main's operator can use this without restarting the session. The command re-reads the profile file and existing `--config` overlays, preserves runtime/CLI override precedence, and reports an effective before/after diff. It updates `modelRoles`, `defaultEffort`, `subagent.agents` (including per-lane model/thinking settings), `subagent.model`, `subagent.modelByDepth`, and `subagent.thinkingLevel` in the same Settings object that the task, eval agent bridge, and vibe spawn resolvers read. New spawns use these defaults; already-created workers retain their own settings snapshots. A deleted routing field returns to normal inheritance/default behavior. Invalid YAML, unreadable files, invalid schema values, and concurrent pending settings saves reject reload rather than silently changing routing or rewriting the file. Unknown model selectors still undergo the normal spawn-time model resolution and credential checks.

## What is not hot-swapped

The command does not replace the running Main model/provider binding or change an existing worker's model/effort. Use the normal explicit session model/effort controls for a live session, or start a new session to pick up its startup binding. All profile settings outside the six fields above remain unchanged by this command and are listed by setting path when their effective disk values differ: restart to load those edits. This includes tool enablement, provider/runtime initialization, transport/bridge settings, lifecycle/concurrency controls, plugin configuration, UI settings, and role presentation/cycle metadata. Agent definition/prompt files, extensions, model catalogs, credentials, profile selection, and environment variables are not reloaded here; their existing dedicated mechanisms or a restart are still needed. No install, daemon restart, or active model rebinding is performed.

## Existing paths and verification

`Settings.init()` is a singleton startup load, not a reload API. `settings_snapshot` journal entries record settings evidence; they do not re-read the YAML file. `/reload-plugins` refreshes plugin/project registries, not profile settings. SIGHUP follows session teardown, not config reload. The new supported programmatic entrypoint is `Settings.reloadConfig()`; it is also the implementation behind the slash command, not a second loader or a process-wide signal hook.

Focused coverage: `bun test packages/coding-agent/test/config-hot-reload.test.ts` inside the repository's supported test sandbox. Tests contrast old/new routing through the real spawn resolver, preserve an existing worker settings fork, verify effort defaults, unchanged unrelated settings, override precedence, field removal, repeat reload, and fail-closed invalid files. No browser or dev server is needed for this configuration command.
